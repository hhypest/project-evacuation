# Проверки изменения

Выберите минимальный набор по изменению, выполните его из корня checkout и запишите фактический результат. Установка редактора — [первый запуск](../getting-started.md); закрепление версии — [toolchain.json](../../tools/toolchain.json).

## 6. Проверки

Основная команда — `./tools/check.ps1 -GodotPath '<редактор>'` (PowerShell 7). Runner `tests/run_tests.gd` реализован для unit/contract/integration/regression/all. GPU проверяется отдельно через `tools/gpu_smoke.gd`, экспорт — через `tools/export.ps1`. Точный редактор и хеши заданы в `tools/toolchain.json`; установка — `tools/setup.ps1`.

Для каждой задачи выбрать подходящий набор:

| Изменение | Минимальная проверка |
| --- | --- |
| Правило сети/прогресса | Unit на изменённый инвариант и значимый отказ |
| Сохранение/загрузка | Контракт, round-trip, повреждённые/неизвестные данные и затронутые миграции |
| Движение/Jolt/гравитация | Интеграционный полигон и фактическое управление в сборке |
| Порталы | Математика + пересечение/коллизии + GPU smoke |
| Уровень/игровая коллизия | Валидатор, прохождение, reset, потеря куба и допустимые обходы |
| Ассет/освещение/звук | Импорт, лицензия, просмотр/прослушивание в сцене и проверка читаемости |
| Документация | Согласованность требований, корректность ссылок и статусов |

Проверка импорта, `--check-only`, unit, интеграция, GPU-smoke и полное прохождение — разные свидетельства. Не выдавать одно за другое. `--check-only` применяется с `--script` и сам по себе не проверяет все скрипты проекта.

Если инструмента, движка, GPU или платформы нет, сделать всё доступное и точно указать непроверенный остаток. Не писать «всё протестировано», когда выполнена только проверка текста. Не создавать бессодержательные тесты, повторяющие строки реализации.


## 5. Проверки и команды

### Реализованный тестовый каркас

Реализован собственный небольшой runner `tests/run_tests.gd` на типизированном GDScript, наследующий `SceneTree`, без стороннего тестового фреймворка. Контракт runner:

- `--suite unit`, `contract`, `integration`, `regression` и `all`; suite `all` выполняет все проверки, доступные без GPU.
- Параметры приложения читаются после `--`; неизвестная suite и отсутствие ожидаемых тестов дают ошибку.
- Печатаются число выполненных/упавших проверок, длительность и версия Godot; сбой возвращает ненулевой exit code.
- У интеграционных сценариев есть ограничение времени/тиков, чтобы зависание не выглядело как успешная проверка.
- Runner не объявляет GPU-smoke или ручное прохождение выполненными по результату headless-прогона.

Команды ниже работают, если закреплённый редактор доступен как `godot`; иначе используйте `& $env:GODOT_BIN` вместо `godot`. Полный проверенный набор, включая все скрипты и отрицательные случаи runner, запускается через `./tools/check.ps1`:

```powershell
godot --headless --path . --script tests/run_tests.gd -- --suite unit
godot --headless --path . --script tests/run_tests.gd -- --suite contract
godot --headless --path . --script tests/run_tests.gd -- --suite integration
godot --headless --path . --script tests/run_tests.gd -- --suite regression
godot --headless --path . --script tests/run_tests.gd -- --suite all
```

Для проверки синтаксиса конкретного скрипта:

```powershell
godot --headless --path . --script src/bootstrap/main.gd --check-only
```

Эта команда не заменяет обход всех собственных `.gd` и выполнение тестов. Автоматизация FND-04 перечисляет скрипты и проверяет их отдельно, проверяет зависимости слоёв, запускает полный CPU-набор при обычной cadence и 30/144 и учитывает сообщения об ошибках/предупреждениях. Одного кода завершения импорта недостаточно, если в журнале есть ошибки скриптов. Подробнее об официальных параметрах: [командная строка Godot 4.7](https://docs.godotengine.org/en/4.7/tutorials/editor/command_line_tutorial.html).

### Матрица проверок

| Область | Автоматические проверки | Игровая/ручная проверка |
| --- | --- | --- |
| Цепи | Таблицы истинности, память, задержки, циклы, независимость от порядка | Видна причина изменения двери/питания |
| Кнопки | Несколько тел, порог нагрузки, удаление, дребезг | Кубы разной массы, наклон, выход из области |
| Свет | Питание, дальность, приёмник, преграда | Читаемость на разных настройках качества |
| Движение | Скорость, ускорение, прыжок, ступени, профиль | Мышь, air control, crouch/duck-jump, лестницы, вода, смена гравитации |
| Перенос | Масса, ограничение силы, отпускание, бросок | Стена, потолок, угол, зажатие и попытка подъёма игрока предметом |
| Гравитация | Приоритет зон, границы, включение, пробуждение | Переход на стену/потолок, комфорт камеры |
| Порталы | Математика, скорость, crossing, занятый выход, питание | Вид, clipping, проходимость, быстрый/удерживаемый куб |
| Сохранение | JSON round-trip, синтаксис/типы/диапазоны, повреждение, неизвестная схема, миграции | Возобновление из меню и после смерти, резерв после прерванной записи |
| Диегетический UI | Типизированные связи представления со сценариями; пауза/фокус/ввод | Носитель в мире, читаемость при FOV/разрешении, клавиатура/мышь, доступность, все важные состояния |
| Сессия/ввод | Меню/старт/пауза/возврат, поколения, сброс удержаний/edges/look, отказ загрузки | Захват курсора, реальные переключения окна, явное продолжение и выход в экспортированной сборке |
| Уровни | ID, соединения, spawn/reset, пары порталов | Решение, допустимые обходы, потеря предметов и выход |
| Ассеты | Импорт, ссылки, ограничения ресурсов | Просмотр/прослушивание в целевой сцене |

Физические тесты задают геометрию, число тиков и допуски. Они не сравнивают координаты побитово между платформами. Тест должен проверять поведение или инвариант, а не повторять строку реализации.

Покрытие каждой механики тестами, контроль независимости от render cadence (`--fixed-fps 30/144`) и ручные проверки на полигоне описаны в [docs/testing.md](../testing.md).

### GPU и экспорт

Vulkan и изображение через портал проверяются на реальном GPU. Записываются фактический драйвер рендеринга, GPU, драйвер ОС, разрешение, качество, версия игры и Godot. Проверить оба направления портала, края проёма, near-plane, оба портала в кадре и включение/выключение питания. Headless-успех не закрывает этот пункт.

Presets уже созданы. После `tools/setup.ps1` используйте `./tools/export.ps1`: он создаёт `builds/`, собирает обе платформы и копирует лицензии рядом с бинарниками. Эквивалентные отдельные команды при существующем каталоге `builds/`:

```powershell
godot --headless --path . --export-release "Windows Vulkan" builds/evacuation.exe
godot --headless --path . --export-release "Linux Vulkan" builds/evacuation.x86_64
```

Каждый заявленный экспорт затем запускается на своей целевой ОС; успешная упаковка не подтверждает запуск. Для изменений, влияющих на runtime, важна экспортированная сборка, а не только редактор. Состояние проверки Linux/Windows указано в отчёте QA.

### CI

`.github/workflows/ci.yml` задаёт pipeline: проверенный по хешу редактор → импорт → типы/слои → unit/contract → интеграция Jolt и регрессия → проверенные export templates → Windows/Linux export. Linux-экспорт дополнительно проходит игровой сценарий через `--runtime-smoke` (ввод, перенос/бросок, кнопка/дверь, портал и аварийный reset), с отрицательной проверкой exit code. Артефакты Windows/Linux включают notices, manifest commit/tree/SHA256 и хранятся 14 дней. Обычный runtime не создаёт диагностический узел без явного флага. Логи находятся в журнале workflow. Валидатор полноценных уровней появится в SYS-02; GPU-smoke и прохождение выполняются отдельно, пока нет подходящего GPU-runner. Проверка, которую инфраструктура ещё не поддерживает, помечается как не выполненная. Наличие YAML не заменяет успешный запуск workflow.


## Документация

Для проверки ссылок нужен Python 3.10+ без внешних пакетов:

```bash
python tools/check_docs.py
```

Проверяются локальные пути/якоря, старые ссылки и карта переноса. Внешние URL учитываются отдельно: сетевой отказ не равен удалению источника. Правка документации не требует игрового GPU-smoke, но изменение инструкции запуска требует воспроизведения на указанной ОС.
